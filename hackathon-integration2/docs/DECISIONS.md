# Расхождения и принятые решения

Правило команды: при расхождении **приоритет у PDF кейса**. Дальше — уточнения организаторов в чате, затем наше ТЗ.

## 1. Что мы строим
| | ТЗ | Кейс (PDF) | Решение |
|---|---|---|---|
| Суть | своя ITSM: создание инцидентов, разработчики/тестировщики, отчёты, ветки, заморозки | **дашборд-помощник координатора**, «визуальный слой», по клику — переход в ITSM | ядро — дашборд над данными выгрузки; канбан — альтернативный сценарий над **реальными** статусами ITSM |
| Пользователь | coordinator / developer / tester / admin | координатор | роли `admin`, `coordinator`, `viewer`. Разработчики и тестировщики живут в ITSM и в данных присутствуют как `assignedEmployee` / `initiatorName` |
| Создание инцидентов | форма создания (но в §4.1 координатору «Нет» — противоречие внутри ТЗ) | инциденты приходят из выгрузки | у нас не создаются: файл / загрузка файла / `POST /ingest/incidents` |
| Отчёты, ветки, заморозка, вложения | есть | нет | вне ядра (идеи на потом, если останется время) |

## 2. Формат данных
- PDF: «дашборд должен работать только с тем форматом, который представлен в файле». Организаторы: поля можно менять и добавлять, но базовый набор обязателен.
- **Решение:** родной формат системы — формат файла (те же имена полей, camelCase). В Mongo запись хранится как есть в `data`, наше — рядом (`meta`, `ai`, `ack`). Экспорт возвращает ровно исходный формат, а экспорт→импорт даёт 0 изменений (проверено).
- Модель `incidents` из ТЗ (number, title, where, what, severity…) не используем: `where` → `productName` / `service`, `what` → `header` / `scenarioName`, `severity` → `priorityId`.

## 3. Статусы
- В файле атрибутов: «7 — Закрыт, 10 — Завершен». В **данных и в ответе организаторов наоборот**: `7 = Завершен (Resolved)`, `10 = Закрыт (Closed)`. Берём данные + ответ.
- Статуса **20 «Исследование ситуации» (Research)** нет в файле атрибутов, но он есть в данных (5 шт.) и это одна из 4 групп кейса. Учтён.
- Семантика: 0/2 — в работе; 20 — проблема решена, идёт разбор причин (требует внимания); 7 — решено, но можно вернуть в работу; 10 — финал, при повторе заводится **новый** инцидент.
- Статусы ТЗ (`to_do/in_progress/qa/done/frozen`) не используем.

## 4. Критичность и сроки
- ТЗ: severity + свой SLA (2/8/24/72 ч). Данные: `priorityId` 1..4 и **готовый `deadline`**. → Срок берём из `deadline`; если его нет (3 записи) → `sla.state = "none"`.
- «Критический» = `priorityId == 4` («Наивысший»), «высокий» = `3`. Оба числа — в настройках (`CRITICAL_PRIORITY_ID`, `HIGH_PRIORITY_ID`).
- ⚠️ В выгрузке **нет ни одного `priorityId = 4`** → на исходных данных группа «Критические» пуста. На демо критический появляется правкой файла.
- Решённый критический остаётся в группе 60 мин с `isResolved: true` («сразу видно, когда такой инцидент решён»). Время решения считается от момента, когда **мы увидели** переход, а не от `completionDate`: на демо `completionDate` может быть любым.

## 5. Группы (может быть несколько сразу)
| Группа | Условие |
|---|---|
| critical | `priorityId == 4` и проблема не решена (+ недавно решённые) |
| coordinators | `assignedGroupName == "КЦ ИТ Координаторы Массовых Инцидентов"` и статус 0/2/20 |
| high | `priorityId == 3` и проблема не решена |
| research | `stateId == 20` |
На исходном файле: critical 0, coordinators 2, high 1, research 5 (закреплено в тестах).

## 6. Качество данных (что чиним при импорте)
- `solution` заполнен у 24 инцидентов в статусах Назначен/Выполняется. Организаторы подтвердили, что так быть не должно → очищаем и пишем предупреждение в отчёт импорта.
- Тексты `urgency`/`impact` в данных («Низкая», «Наивысшее») не совпадают с файлом атрибутов («Низкий», «Наивысший») → опираемся на `*Id`.
- `productId` не уникален для продукта (один id у разных `productName`) → продукт определяем по `productName`.
- `waitingExitDate = "0001-01-01T00:00:00"` — «пусто» → `null`.
- Даты с микросекундами (`.472263Z`) → округляем до мс, потому что Mongo хранит мс; иначе каждый импорт видел бы ложное изменение.
- Если при ручной правке поменяли только текст (`"state": "Завершен"`) и забыли `stateId`, верим тексту; во всех остальных случаях источник истины — id. Всё пишется в предупреждения импорта.

## 7. Файл и изменения
- Файл — «мини-выписка на текущий момент, точка начала». Отслеживаем изменения файла (watchfiles, следим за папкой, т.к. редакторы сохраняют через переименование).
- Инцидент пропал из нового файла → **архив** (логическое удаление), вернулся → восстановлен (`IMPORT_MISSING_POLICY=keep` отключает).
- Правки через API и следующая правка файла: файл = правда ITSM и перетрёт правку из API. Если на демо нужны оба способа сразу — `WRITE_BACK_TO_FILE=true` (бэкенд записывает состояние обратно в файл). Компромисс: ручная правка, сделанная в ту же секунду, может потеряться.
- Внешняя система может пушить изменения: `POST /api/ingest/incidents` (upsert, `X-Service-Key`).

## 10. Переход в ITSM — муляж
Организаторы разрешили муляж. `itsmUrl` в карточке по умолчанию ведёт на встроенную страницу
`http://localhost:8000/itsm/incident/{id}` (список — `/itsm`). На ней видна полная запись, история,
и есть форма «Изменить» (статус, приоритет, группа, исполнитель, срок, подстатус, решение).
Правка в муляже меняет **файл выгрузки**, а не базу напрямую. Дальше обычный путь: импорт → событие → дашборд.
Так на защите видна цепочка «ITSM → выгрузка → дашборд», и файл с базой не расходятся.
Без авторизации (это муляж); выключается `ITSM_MOCK_ENABLED=false`. Для показа с другого компьютера —
`ITSM_BASE_URL=http://<IP>:8000/itsm/incident/`, `DASHBOARD_URL` — адрес фронта (ссылка «на дашборд»).
